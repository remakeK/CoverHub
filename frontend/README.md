# CoverHub — фронтенд

Клиент CoverHub на React, React Router и Vite. Вход и регистрация используют Spring Boot API. Каталог показывает демонстрационные данные. Экраны загрузки кавера можно пройти в браузере, файлы остаются на клиенте.

## Локальный запуск

### В обычный день

Запускай проект, когда он нужен. После включения компьютера запускать команды заранее не требуется.

1. Открой Docker Desktop и дождись запуска движка. В терминале **из корня CoverHub**, где лежит `docker-compose.yml`, запусти бэкенд, PostgreSQL и MinIO одной командой:

   ```powershell
   docker compose up -d
   ```

   `-d` оставляет контейнеры работать в фоне. Если CoverHub уже запущен, этот шаг можно пропустить. Если контейнеры уже созданы и просто остановлены, их также можно запустить кнопкой ▶ у группы CoverHub в Docker Desktop.

2. В другом терминале **из корня CoverHub** запусти фронтенд:

   ```powershell
   cd frontend
   npm.cmd run dev
   ```

   Открой [CoverHub](http://localhost:5173). Пока работаешь с сайтом, оставь этот терминал открытым. После остановки Vite или перезагрузки его нужно запустить снова. Для проверки вёрстки и демонстрационного каталога достаточно Vite. Для входа и регистрации нужен бэкенд.

### При первом запуске

- **Бэкенд.** Если в корне ещё нет `.env`, создай его на основе `.env.example` и укажи `DB_URL=jdbc:postgresql://postgres:5432/cover-hub`, `MINIO_ENDPOINT=http://minio:9010` и `MINIO_BUCKET=covers`. Заполни `DB_USERNAME`, `DB_PASSWORD`, `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD` и задай случайный `JWT_SECRET` длиной минимум 32 байта. Затем выполни `docker compose up --build -d` из корня. `--build` собирает образ бэкенда из исходников. Снова используй этот флаг, когда подтянул изменения бэкенда, которые нужно увидеть локально.
- **Фронтенд.** Установи Node.js (например, 22.12 или новее). В папке `frontend` один раз выполни `npm.cmd ci`. Команда устанавливает зависимости по `package-lock.json`. Повтори её, если после обновления проекта изменился этот файл или если нужно восстановить `node_modules`. После обычной перезагрузки переустановка не нужна.

## Страницы сайта

| Адрес | Что доступно |
|---|---|
| `/` | Перенаправляет в каталог. Главная с топами запланирована. |
| `/catalog` | Каверы и оригиналы, поиск, фильтры, сортировка и «Показать ещё». Данные в `src/data/mockCovers.js` и `src/data/mockSongs.js`. |
| `/register` | Регистрация через API. После успеха открывается вход. |
| `/login` | Вход через API. После успеха открывается каталог с аватаром и кнопкой «Выйти». |
| `/forgot-password` | Экран с сообщением о недоступности восстановления. |
| `/upload` | Шаг 1. Название, исполнение, исполнитель, оригинальная песня и описание. |
| `/upload/files` | Шаг 2. Выбор аудио или видео и обложки, либо ссылка на YouTube. «Опубликовать» неактивна. |
| `/my-covers` | Экран, на который ведёт «Выйти» со второго шага. Список с сервера пока не подключён. |

Предстоит реализовать страницу кавера с плеером, редактирование кавера, страницу оригинальной песни, свой и чужой профиль, редактирование профиля, полный список «Мои каверы», жалобы и админ-панель.

### Что нужно уточнить 

### Регистрация и вход

- Какую минимальную длину пароля оставляем? Сейчас фронт требует 8 символов, а бэк — 6. Предлагаю использовать одинаковый минимум. Фронт сразу показывает ошибки в форме, а бэк проверяет данные при каждом запросе.
- В `POST /auth/register` при неверном формате email в валидации указан текст **«Некорректный формат пароля»**. Нужно **«Некорректный формат email»**. Для занятой почты код предусматривает `409 Conflict`.
- В `POST /auth/login` для пустого email указан текст **«Пароль обязателен»**. Нужно **«Почта обязательна»**. Для неверного формата email текст уже правильный. При неверных данных входа оставляем общий ответ `401 Unauthorized` с сообщением **«Неверный email или пароль»**.
- Давай договоримся об одном формате ошибок. Сейчас фронт читает текст ответа или `message` и `detail` из JSON. Чтобы показать ошибку под нужным полем, нужно получать имя этого поля. Например, для занятой почты можно вернуть `{"field":"email","code":"EMAIL_TAKEN","message":"Пользователь с такой почтой уже зарегистрирован"}`. Для общей ошибки входа достаточно `code` и `message`.
- Как восстанавливаем вход после обновления страницы? `POST /auth/refresh` уже принимает действующий refresh-токен и выдаёт новые токены. Нужно согласовать, как сохраняем refresh-токен между загрузками страницы и когда фронт вызывает этот маршрут.
- Можно добавить защищённый `GET /auth/me` или возвращать **ID, имя и роль** в ответе на вход? Имя нужно для инициалов в аватарке, роль — для отображения админки. Права на действия в админке нужно проверять на бэке.

### Каталог

- Можно расширить `GET /api/covers`, чтобы он отдавал только опубликованные каверы? Для карточек нужны имя исполнителя, обложка, формат, число лайков и прослушиваний. Ещё нужны поиск по названию и исполнителю, фильтры по формату, исполнению, периоду и рейтингу, а также сортировка.
- Для кнопки «Показать ещё» нужна выдача порциями по **8 каверов или 9 оригиналов**. Можно передавать размер порции параметром, а в ответе получать список и общее число результатов.
- Для `GET /api/original-songs` нужно добавить имя исполнителя и поиск по названию песни и исполнителю. Как выбираем оригинал при загрузке кавера, если песни ещё нет в базе?

### Загрузка и «Мои каверы»

- Можно по кнопке **«Далее»** использовать `POST /api/covers`, чтобы создать черновик до загрузки файлов? Предлагаю определять автора по токену и возвращать ID и статус черновика. Нужно понять, откуда брать обязательный `categoryId` и куда передавать исполнителя, тип исполнения и описание.
- Как только пользователь прикрепляет аудио или видео, файл сразу начинает загружаться. Обложка загружается отдельно, как только её прикрепили. Поддерживает ли `POST /api/covers/media/{coverId}` два независимых запроса? Какие форматы и размеры допускаются для каждого файла, обязательна ли обложка и можно ли повторить только ту загрузку, которая завершилась ошибкой? Кто запускает обработку после загрузки?
- Для YouTube пользователь вводит только ссылку. Какие ссылки принимаем — обычные, короткие, Shorts? Кто получает обложку и какую ошибку вернёт API, если видео недоступно?
- Для **«Моих каверов»** нужен список опубликованных каверов и черновиков текущего пользователя. Предлагаю `GET /api/covers/me`. В ответе нужны ID, название, обложка, статус и состояние загрузки файла и обложки. Нужно согласовать, что показывать после выхода со страницы и можно ли продолжить незавершённую загрузку.
- Когда можно нажимать **«Опубликовать»** и каким запросом публиковать? Например, `POST /api/covers/{id}/publish`. Для удаления черновика можно использовать существующий `DELETE /api/covers/{id}`? Удаляются ли при этом файлы из MinIO?
- На бэке нужно проверять владельца при открытии черновика по ID, загрузке файлов, редактировании, публикации и удалении. Тогда каждый пользователь увидит только свои черновики и не сможет открыть или изменить чужой.
